## 9. Rollback plan (Fase 9)

Full procedure: `docs/release-rollback.md` (still DRAFT/UNVERIFIED — this is
the honest state).

```
Deploy → Validate (smoke §15)
   │ fail on >1 item, not fixable in <15 min
   ▼
Rollback trigger
   ▼
Process (in order)
   1. Frontend: redeploy the recorded last-good deployment id
      → public surface is restored in minutes; no data risk
   2. Email: if queue errors, pause the process-email-queue cron,
      drain the queue manually, re-enable after the fix
   3. Database: restore the pre-deploy backup ONLY if a migration ran
      (none run in R20 — so this step is almost certainly unnecessary)
   4. Storage: restore only if media was modified during the window
   5. Verify with the smoke script, then close the incident

Measured: frontend rollback is the fast path and covers every R20 change
(all R20 work is frontend + generated JSON; no schema migration).
```

## 11. Release decision (Fase 18)

### NOT READY — blocked on operator platform actions

**Code status: releasable.** `tsc` clean, 882 tests green, build green, no
secrets, budgets met, no dependency drift, every wave documented and guarded.

**Platform status: not verified.** Eight items require access this audit
does not have. Until they are done, a deploy could silently break email,
cron or booking capture — the exact failure modes a revenue site cannot
afford.

### Blockers (all operator actions)

| # | Blocker | Why it blocks |
|---|---|---|
| B1 | `RESEND_API_KEY` + domain verification | transactional mail is the booking/lead confirmation path |
| B2 | `EMAIL_WEBHOOK_SECRET` + sender re-key | unauthenticated webhook accepts forged events |
| B3 | Cron schedules confirmed (`process-email-queue`, `admin-tasks-sla`, `agentic-scenario-cron`) | queue backs up silently without them |
| B4 | Production database + storage backup with recorded checksum | rollback has no restore point |
| B5 | SPA rewrite (404.html fallback) verified on the host | deep links 404 without it |
| B6 | `admin_tasks` adopt-or-retire decision | blocks the SLA cron |
| B7 | Host rewrite verified in staging **and** production | landing/case deep links are the SEO surface |
| B8 | Rollback rehearsal executed | procedure is unverified until rehearsed |
| B10 | Apply the staged revenue migration (`supabase/migrations_next/20261009_revenue_attribution.sql`) and set `REVENUE_WEBHOOK_SECRET` | without them the CRM cannot write stages, so `revenue_events` stays empty and the revenue panels stay in empty state |

Once B1–B8 are done and §8 is executed, this release becomes READY without
any further code change. B10 gates the R20.18 revenue panels, not the site:
nothing on a public page depends on it.

## 15. R21.1B — platform verification outcome

**New finding (B2).** `auth-email-hook` accepts `EMAIL_WEBHOOK_SECRET` **or**
the legacy `LOVABLE_API_KEY`. The endpoint therefore authenticates even when
the new secret is unset — so "the webhook works" does not prove "the secret is
configured". Verify the secret explicitly (runbook B2.1), and only then
re-key the sender and delete the fallback.

**New finding (B6).** `admin_tasks` is an active queue with no operator
surface: the SLA cron manages rows no human can see. Not a release blocker;
documented so it is a known blind spot rather than a surprise.
